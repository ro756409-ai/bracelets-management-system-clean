## أولًا — 0053: قيد فريد على `orders(businessId, externalOrderId)`

### المشكلة الحالية
| المسار | الآلية اليوم | الفجوة |
|---|---|---|
| استيراد Excel (EasyOrder) | تخطّي Order ID الموجود داخل النشاط تحت **قفل صف النشاط** (`FOR UPDATE`) داخل معاملة الدفعة | لا قيد في القاعدة؛ الحماية تعتمد على أن كل كاتب يأخذ نفس القفل |
| EasyOrder webhook | `getOrderByExternalId` ثم إدخال — **بلا قفل وبلا قيد** | تسليمان متزامنان، أو webhook + استيراد Excel، ينشئان نسختين |

في مخطط الاختبار لا يوجد أي فهرس على `businessId` أو `externalOrderId` في `orders` (فقط PK و`orderNumber`/`serialNumber`).
الفحص المسبق يعرض الفهارس الفعلية لكل بيئة.

### الـDDL المقترح
```sql
ALTER TABLE `orders`
  ADD UNIQUE INDEX `orders_business_external_unique` (`businessId`, `externalOrderId`),
  ALGORITHM=INPLACE, LOCK=NONE;
```
- **الكتابات العادية مستمرة أثناء بناء الفهرس.** لو أُدخل تكرار أثناء البناء، تفشل الـDDL كاملة بلا أي أثر، ويُعاد تشغيلها.
- **الفهرس يسرّع البحث أيضًا:** يخدم `getOrderByExternalId` وقراءات النشاط، لأن `businessId` أول عمود فيه.

### القيم الفارغة والترتيب (Collation)
| الحالة | سلوك القيد | المعالجة |
|---|---|---|
| `NULL` | لا يتعارض (أوردرات بلا معرّف خارجي غير متأثرة) | لا شيء |
| `''` أو مسافات فقط | **قيمة** تتعارض لو تكررت في نفس النشاط | الفحص يعدّها؛ التطبيق لا يكتبها (Excel: `|| undefined`، webhook: يرفض الفارغ). وجودها = بيانات قديمة ⇒ تحويلها إلى `NULL` بخطوة بيانات معتمدة منفصلة |
| اختلاف حالة الأحرف/التشكيل فقط (`abc`/`ABC`) | **يتعارض** (`utf8mb4_0900_ai_ci`) | الفحص يعدّها منفصلة (`caseOrAccentVariantGroups`) |
| مسافة طرفية (`B-1` / `B-1 `) | **لا يتعارض** (`NO PAD`) | الفحص يعرضها للعلم (`paddedKeys`) |
| نفس المفتاح في نشاطين | مسموح (القيد داخل النشاط) | للعلم (`crossBusinessKeys`) |

اختُبر توقّع الفحص مقابل القيد الفعلي على قاعدة مؤقتة (8.4 و8.0): نفس المجموعات تمامًا.

### التكرارات الموجودة
- **الـMigration ترفض التطبيق ما دامت هناك أي مجموعة مكررة.** فحص الجاهزية يُستدعى داخل apply نفسه، ولا يوجد دمج أو حذف تلقائي.
- **الفحص يعرض كل مجموعة:** النشاط، وعدد الصفوف، ومعرّفات وأرقام الأوردرات، وحالاتها، ومصادرها، وأول وآخر تاريخ. لا يعرض بيانات العملاء.
- **الحسم لكل مجموعة بقرار المالك:**
  - أيّ أوردر يحتفظ بالمعرّف.
  - الباقي يُعاد تسميته إلى `<المعرّف>#dup<id>`، فيبقى الأوردر وتاريخه كما هما.
  - القيم الفارغة تتحول إلى `NULL`.
  - ينفّذ ذلك سكربت بيانات **منفصل** بموافقة ونسخة احتياطية، ويُسجَّل في سجل النشاط. لم يُكتب.

### التزامن بين Excel والـwebhook بعد 0053
- **Excel:** قراءة القفل `SELECT … FOR UPDATE` على `(businessId, externalOrderId IN …)` تستخدم الفهرس الجديد، فتقفل قيم المفاتيح نفسها.
  - إذا كتب الـwebhook نفس المفتاح أولًا، يراه Excel تحت القفل ويتخطّاه.
  - إذا بدأ Excel أولًا، ينتظر إدخال الـwebhook حتى يلتزم Excel، ثم يفشل بـ`ER_DUP_ENTRY`.
- **تعديل الكود المطلوب مع 0053:**
  - **webhook:** عند `ER_DUP_ENTRY` على `orders_business_external_unique` يعيد قراءة الأوردر الموجود ويسلك مسار «موجود» (تحديث إن كانت البيانات أحدث، أو `duplicate_unchanged`)، بدل الخطأ.
  - **Excel:** حماية احتياطية لكل صف داخل الدفعة. خطأ التكرار يلغي العبارة فقط (الهيدر، قبل البنود)، فيُعدّ الصف «موجودًا» وتستمر الدفعة.
- **قبل 0053:** يبقى السباق ممكنًا. الكود الجديد يعمل بنفس الطريقة مع الفهرس أو بدونه.

### خطة check / apply / replay / verify / rollback
- **محرّك مخصص** مثل 0046 (‏`ALTER` وليس `CREATE TABLE`)، والحالات: `not_applied`، `applied` (فهرس بنفس الاسم والأعمدة وفريد)، `partial` (اسم موجود بتعريف مختلف).
- **apply:** بوابات البيئة وعبارة التأكيد، والإنتاج مرفوض في هذه المرحلة. ثم الفحص المسبق داخليًا، ويرفض إن لم يكن «جاهز». ثم الـDDL، ثم التحقق.
- **replay:** الفهرس موجود ⇒ لا تغيير.
- **rollback:** `DROP INDEX` مسموح دائمًا، فلا يحذف بيانات. لكنه يعيد السباق، والكود يتحمّل الحالتين.
- **الاختبارات:** مطابقة الفحص للقيد (منفّذة الآن)، والرفض مع التكرارات، وwebhook وExcel متزامنان ينتجان نسخة واحدة، والـreplay، والـrollback.

## ثانيًا — واتساب وصفوف Excel بلا Order ID

### الخيارات
| الخيار | الوصف | التقييم |
|---|---|---|
| مفتاح بادئة في `externalOrderId` | `wa:<hash>` في نفس العمود | **مرفوض:** يحمّل الحقل معنى جديدًا. `getOrderByExternalId` وكشف التكرار يعاملانه كمعرّف EasyOrder، والقيد 0053 سيطبَّق على مفاتيح مصطنعة |
| **جدول 0052 + قيمة عملية جديدة (0054)** | `operation = 'order.import_row'`، ومفتاح لكل صف | **المقترح:** الجدول بنفس الشكل المطلوب، بقيده الفريد ونطاقه وحماية «لا تعديل ولا حذف» واختباراته. الـMigration مجرد إضافة قيمة في آخر الـenum |
| جدول مستقل | `order_import_row_keys` | فصل أنظف للمفهوم، لكنه Migration أكبر ومنطق حماية مكرر |

**لماذا قيمة enum جديدة وليس `order.create` ببادئة؟** معرّفات `order.create` يرسلها العميل. لو شاركته مفاتيح الصفوف نفس قيمة العملية، يستطيع عميل نظريًا حجز مفتاح صف. القيمة المستقلة لا يكتبها إلا مسار الاستيراد على السيرفر.

### 0054 المقترحة (معدّلة)
```sql
-- (1) قيمة العملية — إضافة في آخر القائمة: تعديل تعريف فوري بلا إعادة بناء
ALTER TABLE `operation_idempotency_keys`
  MODIFY COLUMN `operation` enum('order.create','workshop.send','order.import_row') NOT NULL, ALGORITHM=INSTANT;
-- (2) فهرس غير فريد للبحث عن التشابه ببصمة المحتوى داخل النشاط
ALTER TABLE `operation_idempotency_keys`
  ADD INDEX `oik_scope_content_idx` (`tenantId`, `businessId`, `operation`, `requestHash`), ALGORITHM=INPLACE, LOCK=NONE;
```
- **الحالات:** `applied` = القيمة والفهرس موجودان بالتعريف الصحيح. `partial` = واحد منهما فقط أو تعريف مختلف، فيُرفض التطبيق بلا إكمال تلقائي. `not_applied` = تعريف 0052 كما هو.
- **check:** يقرأ تعريف الـenum والفهرس ويقارنهما بتعريف 0052 المتوقع.
- **rollback:** مرفوض متى وُجد أي صف `order.import_row`، ويحذف الفهرس ويعيد القائمة فقط عندما لا يوجد.
- 0052 مطبّقة على Staging، لذلك هذه Migration مستقلة، لا تعديل على 0052.

### المفهومان منفصلان
| المفهوم | ما هو | من يولّده | الغرض | أين يُخزَّن |
|---|---|---|---|---|
| **بصمة المحتوى `C`** | sha256 لمحتوى الصف القانوني | السيرفر من الملف (لا يثق بالعميل) | **اكتشاف التشابه فقط**: «هذا الصف يشبه أوردرًا مستوردًا سابقًا أو صفًا آخر في الملف» | `requestHash` في صف 0052 (+ فهرس `oik_scope_content_idx`) |
| **معرّف المحاولة `A`** | معرّف عشوائي ثابت لعملية استيراد واحدة لملف واحد | الواجهة (`persistentOperationIdFor`) بنطاق: الجلسة + النشاط + المصدر + بصمة الملف | **منع تكرار الحفظ**: نفس المحاولة لا تحفظ الصف مرتين | يدخل في `operationId` لكل صف |
| **معرّف صف المحاولة** | `ir_` + H(A ‖ C ‖ k) للصف العادي، `io_` + H(A ‖ C ‖ k ‖ choiceId) للاستيراد رغم التطابق | السيرفر | المفتاح الفريد الذي يمنع حفظ نفس الصف مرتين في نفس المحاولة | `operationId` (فريد في نطاق الشركة/النشاط/العملية) |
| **رقم التكرار `k`** | ترتيب الصف بين صفوف **نفس البصمة** داخل الملف (1، 2، …) | السيرفر | تمييز الصفوف المتطابقة داخل الملف دون الاعتماد على رقم السطر (إعادة الترتيب لا تغيّر شيئًا) | داخل H |
| **معرّف الاختيار الصريح `choiceId`** | معرّف عشوائي يُولَّد عند ضغط المستخدم «استيراد رغم التطابق» لصف بعينه | الواجهة، ومحفوظ في تخزين التبويب بنطاق (A، C، k) | يجعل الاستيراد المقصود **ثابتًا عبر فقدان الرد وإعادة التحميل** | داخل H لصفوف `io_` |

**البصمة `C`:**
- **تشمل:** الهاتف المطبّع، والاسم، والمحافظة، والعنوان المطبّع (توحيد أ/إ/آ وة/ه وى/ي والأرقام، وضغط المسافات)، ونص كل منتج الخام المطبّع مع الكمية مرتّبة، والإجمالي بمنزلتين، وتاريخ الأوردر في Excel إن وُجد.
- **لا تشمل:** الملاحظات، ولا اسم الصفحة أو الإعلان، ولا رقم السطر، ولا اسم الملف، ولا **المصدر**. هكذا يُكتشف نفس الأوردر وإن جاء مرة من واتساب ومرة من Excel.

### خطوات السيرفر لكل صف (داخل `importOrdersAtomic` تحت قفل صف النشاط، والدفعة كلها تنجح أو تُلغى)
1. **معرّف صف المحاولة موجود؟** ⇒ إعادة نتيجة: نفس الأوردر، والحالة «حُفظ في هذه المحاولة». البصمة المخزنة يجب أن تساوي `C`، وإلا رفض للصف (لا يحدث إلا بتلاعب، لأن تعديل الملف يغيّر بصمته فيغيّر `A`).
2. **`k ≥ 2` أو `C` موجودة سابقًا في النشاط** (من أي مستخدم، وأي مصدر)، ولا يوجد اختيار صريح لهذا الصف ⇒ **تخطٍّ**، مع ذكر الأوردرات المطابقة: الرقم، ومن استوردها، ومتى.
3. **يوجد اختيار صريح** (`choiceId` لهذا (C، k)) ⇒ حفظ أوردر جديد بمعرّف `io_…`، وتسجيل في سجل النشاط: من، ولماذا، والأوردر المطابق السابق.
4. **غير ذلك** ⇒ حفظ أوردر جديد بمعرّف `ir_…`.

القيد الفريد على `operationId` حماية احتياطية من التكرار، فوق القفل.

### السيناريوهات
| الحالة | النتيجة |
|---|---|
| **إعادة محاولة نفس الاستيراد** (ضاع الرد، أو أُعيد تحميل الصفحة ثم اختير نفس الملف) | نفس بصمة الملف ⇒ نفس `A` من تخزين التبويب ⇒ نفس معرّفات الصفوف ⇒ **نفس الأوردرات تُعاد**، بلا أي حفظ جديد |
| **استيراد مقصود رغم التطابق** | يضغط المستخدم «استيراد رغم التطابق» للصف ⇒ `choiceId` ثابت محفوظ. فقدان الرد أو إعادة التحميل ⇒ نفس `choiceId` ⇒ **نفس الأوردر يُعاد**. **نسخة أخرى** تحتاج محاولة جديدة **واختيارًا صريحًا جديدًا** (`choiceId` جديد)، لأن الصف سيظهر مطابقًا أيضًا لنسخة الاختيار السابق |
| **إعادة الاستيراد بواسطة مستخدم آخر** | `A` الخاص به مختلف، فلا إعادة نتيجة بين المستخدمين. التشابه بالبصمة **على مستوى النشاط** ⇒ صفوفه تظهر «مستوردة سابقًا بواسطة فلان — #X» وتُتخطّى افتراضيًا. الاستيراد رغم ذلك باختيار صريح منه، ويُسجَّل باسمه. لو أرسل معرّف محاولة مستخدم آخر ⇒ رفض بلا تفاصيل (قاعدة 0052) |
| **تغيير الملاحظات فقط** | البصمة لا تشمل الملاحظات ⇒ الصف **مطابق** ⇒ يُتخطّى، والمعاينة تقول «مطابق — الملاحظات فقط مختلفة (#X)». **لا تحديث صامت** للأوردر القائم؛ تعديل الملاحظات يكون من التطبيق. الاختيار الصريح هنا ينشئ أوردرًا جديدًا، وهو نادرًا ما يكون المطلوب، والمعاينة تنبّه لذلك |
| **صفوف متطابقة داخل الملف** | الأول (`k=1`) يُعامل عاديًا. الثاني فما بعده «مكرر داخل الملف (مثل السطر n)» ويُتخطّى افتراضيًا، والاستيراد باختيار صريح لكل صف بمعرّفه الثابت |
| **ملف معدّل** | بصمة الملف تتغيّر ⇒ `A` جديد. الصفوف غير المتغيرة مطابقة بالبصمة ⇒ تُتخطّى. الصف المتغير في حقل هوية ⇒ أوردر جديد، مع تنبيه «مشابه لأوردر سابق (نفس الهاتف)». لا تحديث للأوردر القديم |
| **صفوف Excel التي فيها Order ID** | خارج هذا التصميم: منع التكرار بالمعرّف (0053) كما هو |

### الواجهة
- **قبل المعاينة:** بصمة الملف sha256 تُحسب في المتصفح (`crypto.subtle`)، ثم `A = persistentOperationIdFor("order.import|<الجلسة>|b<النشاط>|<المصدر>|<بصمة الملف>")`.
- **المعاينة:** تعرض لكل صف تصنيفه (جديد / مطابق سابقًا / مكرر داخل الملف / الملاحظات فقط مختلفة) مع المطابقات. زر «استيراد رغم التطابق» لكل صف، ولا يوجد «استيراد الكل رغم التطابق» افتراضيًا.
- **التنفيذ:** يرسل `A`، وقائمة الاختيارات الصريحة `{C, k, choiceId}`. السيرفر يعيد حساب `C` و`k` من الملف نفسه.
- **عند النجاح:** يُستهلك `A` وتُستهلك الاختيارات. عند فقدان الرد يبقيان.
- **عند CONFLICT:** لا تغيير تلقائي للمعرّفات (نفس قاعدة الشاشات الأخرى).

## الفحص المسبق (قراءة فقط) — جاهز ولم يُشغَّل على Production
- **التشغيل:** `node dist/scripts/check-external-order-ids.mjs [--json] [--limit N]`.
- **الأمان:**
  - جلسة `READ ONLY`، والمنفّذ يرفض أي عبارة غير `SELECT`.
  - القاعدة التي تبدو إنتاجًا تُرفض إلا مع `--i-understand-production`. التشغيل على Production يحتاج موافقة منفصلة.
- **رمز الخروج:** 0 جاهز، 1 تكرارات أو فهرس متعارض، 2 خطأ، 3 إنتاج بلا إقرار.
- **المخرجات:**
  - تعريف العمود وترتيبه، والفهارس ذات الصلة، وحالة الفهرس المقترح.
  - عدد الأوردرات وقيم NULL والفارغة والمسافات الطرفية.
  - المجموعات المكررة، ومنها الفارغة وفروق الحالة، مع عينات بالأرقام والحالات والمصادر.
  - المفاتيح المشتركة بين أنشطة.
- **اختبار ‎`externalOrderIdPrecheck.db.test.ts`:** القيد يُنشأ عند «جاهز»، ويفشل بنفس المجموعات عند «غير جاهز»، والمنفّذ لا يكتب.

### تشغيل الفحص على Staging (يدويًا بعد النشر — Production مؤجّل)
1. **إتاحة السكربت:** ملف `scripts/check-external-order-ids.ts` موجود في commit محلي (`0f4f19a` وما بعده)، وغير مرفوع.
   - يُتاح على Staging بعد **Push** للفرع ثم **Deploy** للـcommit المعتمد.
   - البناء (`pnpm build`) ينتج `dist/scripts/check-external-order-ids.mjs`.
   - النشر يشمل أيضًا تغييرات الكود المحلية الأخرى في الفرع (ربط 0052 بالأوردر الجديد والتكرار وبوابة المدير).
2. **في Terminal حاوية تطبيق Staging** (`/app`)، تأكد من وجود السكربت:
   ```bash
   ls dist/scripts/check-external-order-ids.mjs
   ```
3. **التشغيل** (قراءة فقط: جلسة `READ ONLY`، والمنفّذ يرفض غير `SELECT`):
   ```bash
   node dist/scripts/check-external-order-ids.mjs --limit 50
   ```
   - السطر الأول يطبع `الهدف: <host> / <db>`. **تأكد أنه قاعدة Staging.**
   - **رمز الخروج 3 («يبدو إنتاجًا»):** اسم القاعدة لا يحتوي `test` ولا `staging` (الكلمة `stage` وحدها لا تكفي هنا). **توقف** وتحقق من الهدف. لا تُضِف `--i-understand-production` إلا بعد التأكد أنه Staging وبموافقة.
4. **نسخة كاملة للمراجعة** (JSON داخل الحاوية):
   ```bash
   node dist/scripts/check-external-order-ids.mjs --json --limit 200 > /tmp/precheck-0053-staging.json; echo "exit=$?"
   ```
5. **قراءة النتيجة:**
   - `0` = جاهز.
   - `1` = تكرارات أو فهرس متعارض. أرسل العدد والعينات، **بلا أي تعديل أو إعادة تسمية للبيانات**.
