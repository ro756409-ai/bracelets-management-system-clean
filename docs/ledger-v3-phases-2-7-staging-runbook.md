# Runbook — مراحل الدفتر 2–7 على Staging (Migrations ‏0045–0052 وخطة الرجوع)

> **غير مصرّح بتنفيذه حاليًا.** الموافقة الحالية محلية فقط: لا Push، لا Deploy، لا تطبيق Migrations ولا تفعيل
> Ledger على Staging أو Production. هذا الدليل جاهز لقرار لاحق منفصل.

نفس قواعد `docs/ledger-v3-staging-runbook.md`: الأوامر تُلصق في **Terminal حاوية تطبيق Staging** (المجلد `/app`)،
`DATABASE_URL` و`DEPLOY_ENV` من Environment Variables فقط، لا SQL يدوي، وكل سكربت يرفض الهدف الذي يبدو إنتاجًا.
`<db>` في عبارات التأكيد = اسم قاعدة Staging كما يطبعه أمر `--check` (السطر الأول: `الهدف: <host> / <db>`).

> **حالة Staging (حسب المالك، 2026-10-14 — آخر معلوم):** 0052 **طُبّقت وتُحقّق منها** على Staging. في النشر القادم: **فحص
> 0052 فقط** (check قراءة فقط ثم replay)، وأي فرق غير متوقع ⇒ **توقف ومراجعة** (لا تطبيق ولا إصلاح يدوي). خطوة الإيقاف أدناه
> تخص بيئة لم تُطبَّق عليها 0052 بعد (مثل Production لاحقًا). باقي Migrations الدفتر (0045–0051) وتفعيل الدفتر **معلّقة**.

### النشر القادم على Staging (0052 مطبّقة) — بالترتيب
1. Backup، ثم Deploy للـcommit المعتمد (لا حاجة لـ`OPERATION_CREATION_PAUSED` لأن جدول 0052 موجود).
2. فحص 0052 (قراءة فقط): `node dist/scripts/migrate-0052-operation-idempotency.mjs` ⇒ `حالة 0052: مطبَّقة` بلا أي سطر فرق،
   ثم `--apply --confirm "APPLY 0052 TO <db>"` ⇒ `↻ replay بلا أي تغيير`. **أي partial/فرق ⇒ توقف ومراجعة.**
3. `node dist/scripts/check-ledger-prereqs.mjs` ⇒ `0052 … present` (وجداول الدفتر الجديدة `absent` متوقعة — معلّقة).
4. التحقق بالمتصفح من منع التكرار (القسم «التحقق من منع التكرار بعد 0052» أدناه) لكل الشاشات المحمية.
5. (اختياري، قراءة فقط) فحص 0053 المقترحة: `node dist/scripts/check-external-order-ids.mjs` — تقرير فقط، لا تطبيق.

## 0) بيئة لم تُطبَّق عليها 0052 بعد: إيقاف إنشاء الأوردرات وإرسال الورشة، ثم نشر الكود

**لماذا الإيقاف:** بين نشر الكود وتطبيق 0052 والتحقق منها لا يوجد جدول منع التكرار. الواجهة الجديدة ترسل معرّف عملية فتُرفض
طلباتها تلقائيًا (fail-closed)، لكن واجهة قديمة مفتوحة في متصفح (بلا معرّف) كانت ستُنشئ أوردرات/إذونات **غير محمية**. الإيقاف
التشغيلي يرفض العمليتين للجميع خلال هذه الفترة، بلا أي كتابة، برسالة «متوقف مؤقتًا أثناء تحديث النظام».

0. في Environment Variables لتطبيق Staging (Coolify) أضف **قبل** النشر: `OPERATION_CREATION_PAUSED=true`.
1. Deploy لنفس الـcommit المعتمد على تطبيق Staging (الصورة تُبنى بـ`pnpm build` فتنتج `dist/scripts/*.mjs`).
   **العلم `LEDGER_V3` يبقى مطفأ**، و`ACCOUNTING_MODULE_ENABLED` كما هو. الكود الجديد بلا جداوله الجديدة يعمل بالسلوك
   القديم (كل مسار يتحقق من وجود جداوله ويعرض «غير متاح قبل 00NN») — **باستثناء** إنشاء الأوردر وإرسال الورشة: موقوفان
   بالإيقاف حتى 0052 والتحقق منها، والطلب بمعرّف يُرفض أصلًا ما دامت 0052 غير مطبّقة.
2. تحقق من وجود السكربتات داخل الحاوية:

```bash
ls dist/scripts | grep -E "^(migrate-004[5-9]|migrate-005[012]|check-ledger-prereqs|legacy-recovery|disable-ledger-v3)" ; ls drizzle | grep -E "^00(4[5-9]|5[012])_"
```

المتوقع: `migrate-0045-roles.mjs` … `migrate-0052-operation-idempotency.mjs`، `check-ledger-prereqs.mjs`،
`legacy-recovery.mjs`، `disable-ledger-v3.mjs`؛ وملفات SQL ‏0045–0052 (السكربت يقرؤها من `drizzle/`). **نقطة توقف**: أي ملف ناقص =
الصورة ليست من هذا الـcommit.

3. `node -e "console.log({DEPLOY_ENV: process.env.DEPLOY_ENV, paused: process.env.OPERATION_CREATION_PAUSED})"` يجب أن يطبع
   `DEPLOY_ENV: 'staging'` و`paused: 'true'`. **نقطة توقف** إن لم يكن الإيقاف مفعّلًا.
4. تحقق من الإيقاف فعليًا: حفظ أوردر من شاشة الإدخال وإرسال دفعة للورشة يرفضان برسالة «متوقف مؤقتًا…» ولا يظهر أي سجل جديد.

## 1) Backup

نسخة كاملة لقاعدة Staging قبل أي DDL، واحفظ اسمها ووقتها. لا متابعة بلا نسخة مؤكدة.

## 2) فحص المتطلبات (قراءة فقط) — قبل أي Migration

```bash
node dist/scripts/check-ledger-prereqs.mjs
```

اقرأ المخرجات في قسمين **منفصلين**:

| القسم | الشكل | المعنى | القرار |
|---|---|---|---|
| جداول التشغيل المطلوبة (`[الطلبات]`، `[المخزون]`، `[الشحن]`، `[المرتبات]`، `[الحضور (0042)]`…) | `✗ … — الجدول غير موجود` أو `أعمدة ناقصة` | جدول **قائم** تعتمد عليه مسارات الدفتر غير موجود في القاعدة | **نقطة توقف** — رمز الخروج 1. لا تطبّق أي Migration؛ هذه جداول لا تنشئها Migrations الدفتر |
| `أرشيف V1/V2` | `غير موجود (اختياري)` | الكود يتجاهل الجدول الغائب | للعلم فقط |
| `0045` / `0046` (قيم enum) | `· … — غير مطبّقة` | متوقع قبل التطبيق | تُطبَّق في الخطوة 3 |
| `0040`، `0047`–`0052` | `absent` | **جداول جديدة متوقع غيابها** قبل تطبيق Migrations | تُطبَّق في الخطوة 3 |
| أي marker | `partial` | جزء من جداول Migration موجود | **نقطة توقف** — راجع قبل أي apply |

رمز الخروج: 0 = المتطلبات القائمة كاملة (غياب جداول 0047–0052 لا يغيّره)، 1 = جدول/عمود تشغيل مطلوب ناقص، 2 = خطأ
تشغيل، 3 = هدف يبدو إنتاجًا.

حالة 0040 على Staging مسجّلة لدي **كآخر معلوم** فقط («طُبّقت وتحققت، الدفتر معطّل» حسب المالك بتاريخ 2026-10-12) — يؤكدها
هذا الفحص (`0040 … present`) أو `node scripts/migrate-0040-ledger-v3.cjs --check` قبل الاعتماد عليها.

## 3) Migrations — لكل واحدة: check → apply → check → replay

**الترتيب:** 0052 **أولًا** (لتقصير فترة الإيقاف — لا تعتمد على جداول الدفتر، تتطلب الفهرس المركّب businesses(tenantId, id)
من 0040/0041 فقط ويفحصه preflight)، ثم رفع الإيقاف (3أ)، ثم Migrations الدفتر **0045 → 0046 → 0047 → 0048 → 0049 → 0050 →
0051** (0046–0051 تتطلب 0040، و0047–0051 تتطلب الفهرسين المركّبين). Migrations الدفتر لا تمس إنشاء الأوردرات أو الورشة.

**Migration مطبّقة بالفعل** (مثل 0045 على Staging حسب آخر معلوم): تُفحص فقط — `check` يجب أن يطبع `مطبَّقة` بلا أي فرق، ثم
apply يطبع `replay بلا أي تغيير`. **لا rollback ولا إعادة إنشاء.** إن طبع `partial`/فرقًا ⇒ نقطة توقف ومراجعة، لا إصلاح يدوي.

لكل `<id>` و`<script>` من الجدول:

| id | script |
|---|---|
| 0052 | `migrate-0052-operation-idempotency` |
| 0045 | `migrate-0045-roles` |
| 0046 | `migrate-0046-ledger-kinds` |
| 0047 | `migrate-0047-ledger-carrier` |
| 0048 | `migrate-0048-ledger-payroll` |
| 0049 | `migrate-0049-ledger-suppliers` |
| 0050 | `migrate-0050-ledger-snapshots` |
| 0051 | `migrate-0051-ledger-legacy-archive` |

```bash
node dist/scripts/<script>.mjs
```
المتوقع: `حالة <id>: غير مطبَّقة`، وكل أسطر preflight ✓ (لـ0047–0052). **توقف** إن كانت «جزئية» أو أي preflight ✗.

```bash
node dist/scripts/<script>.mjs --apply --confirm "APPLY <id> TO <db>"
```
المتوقع: رمز الخروج 0 وسطر نجاح ✓ (لـ0047–0052: كل عبارة `✓ … نُفِّذ وتحقّق` ثم `✓ <id> مطبَّقة ومطابقة للمواصفة بالكامل`).

التحقق بعد التطبيق (قراءة فقط):
```bash
node dist/scripts/<script>.mjs
```
المتوقع: `حالة <id>: مطبَّقة` بلا أي سطر فرق (✗).

إعادة التطبيق (replay — يجب ألا يغيّر شيئًا):
```bash
node dist/scripts/<script>.mjs --apply --confirm "APPLY <id> TO <db>"
```
المتوقع: `↻ مطبَّقة مسبقًا — replay بلا أي تغيير`، رمز الخروج 0.

**نقاط توقف**: رمز خروج 3 (رفض: بيئة/عبارة/partial/preflight) أو 1 (فشل عبارة) — لا تنتقل للتالية. فشل عبارة يترك
`partial` ظاهرًا (DDL في MySQL غير معاملاتي)؛ لا إكمال يدوي — ارجع للنسخة أو rollback الموثّق.

### 3أ) بعد 0052 مباشرة (قبل Migrations الدفتر): التحقق ثم رفع الإيقاف
1. `node dist/scripts/migrate-0052-operation-idempotency.mjs` ⇒ `حالة 0052: مطبَّقة` بلا فرق، وإعادة apply ⇒ replay (أعلاه).
2. `node dist/scripts/check-ledger-prereqs.mjs` ⇒ `0052 … present`.
3. احذف `OPERATION_CREATION_PAUSED` من Environment Variables (أو اجعلها `false`) وأعد تشغيل التطبيق، ثم
   `node -e "console.log(process.env.OPERATION_CREATION_PAUSED)"` ⇒ `undefined`/`false`.
4. التحقق اليدوي من منع التكرار (القسم التالي). **نقطة توقف**: أي تكرار ⇒ أعد الإيقاف (الخطوة 0) وتوقف.

إذا تعذّر تطبيق 0052 أو التحقق منها: **يبقى الإيقاف مفعّلًا** (أو ارجع للنسخة السابقة من الكود) — لا رفع للإيقاف بلا 0052 متحقق منها.

```bash
node dist/scripts/check-ledger-prereqs.mjs
```
المتوقع: المتطلبات كاملة، `0045`/`0046` ✓، وكل markers `0040`،`0047`–`0052` = `present`.

### التراجع (rollback) — قبل وجود بيانات فقط
`--rollback --confirm "ROLLBACK <id> TO <db>"` بترتيب عكسي لما طُبّق (0051 … 0045، و0052 أخيرًا — وقبل تراجع 0052 أعد
الإيقاف `OPERATION_CREATION_PAUSED=true`، وإلا تُرفض طلبات الواجهة الجديدة). يُرفض تلقائيًا (`not_empty` /
`kind_in_use` / دور مستخدم) متى وُجدت بيانات — **0051 يُرفض مع أي حدث** في سجل الأرشيف، و**0052 مع أي مفتاح عملية**. بعد وجود بيانات: إطفاء العلم فقط.

### التحقق من منع التكرار بعد 0052 — متصفح حقيقي على Staging (بعد رفع الإيقاف)

طريقة «فقدان الرد بعد الحفظ»: أدوات المطوّر ← Network ← اختر طلب الحفظ (`addOrder` أو `workshopSend`) وتابع: افصل الشبكة
(Offline) **بعد** ضغط الحفظ مباشرة وقبل وصول الرد، أو استخدم Request blocking للرد فقط. بعد كل بند: قائمة الأوردرات/الدفعات
وحركة المخزون هي المرجع (عدد السجلات)، لا رسالة الواجهة وحدها.

**شاشة إدخال الأوردرات** (موظف إدخال):
1. حفظ ناجح مع فقدان الرد ⇒ رسالة خطأ شبكة والنموذج يحتفظ ببياناته. أعد الحفظ بلا تعديل ⇒ «الأوردر محفوظ بالفعل — رقم X»،
   وأوردر **واحد** فقط في «أوردراتي».
2. كرر (1) ثم **أعد تحميل الصفحة** قبل إعادة الحفظ؛ أدخل نفس البيانات (أو استرجع المسودة) واحفظ ⇒ نفس الرقم، أوردر واحد.
3. اختلاف البيانات بنفس المفتاح: حفظ مع فقدان الرد، ثم عدّل الكمية أو الهاتف واحفظ ⇒ شريط «البيانات اختلفت عن طلب سابق (X)»
   ولا أوردر جديد؛ إعادة الحفظ ⇒ نفس الرفض. «بدء عملية جديدة» ثم حفظ ⇒ أوردر جديد واحد (عملية جديدة صريحة).
4. تبويبان مستقلان: افتح الشاشة في تبويبين، احفظ أوردرًا بنفس البيانات من كل تبويب ⇒ أوردران (عمليتان مستقلتان)، وفي كل تبويب
   إعادة الحفظ بعد فقدان الرد تعيد أوردر ذلك التبويب فقط.
5. «مسح النموذج» بعد فقدان رد ⇒ الحفظ التالي عملية جديدة.

**نموذج «أوردر جديد» في `/orders`** (المالك/المدير — مسار `orders.create`): في Network يجب أن يحمل طلب `orders.create`
الحقل `operationId`، والرد `idempotency: "protected"` (رد بلا هذا الحقل = نسخة قديمة من الكود ⇒ نقطة توقف). ثم نفس البنود 1–3:
حفظ مع فقدان الرد ثم إعادة الحفظ (النافذة تحتفظ بالبيانات) ⇒ «الأوردر محفوظ بالفعل — رقم X»؛ إعادة تحميل الصفحة ثم فتح النافذة
وإدخال نفس البيانات ⇒ نفس الرقم؛ بيانات مختلفة بنفس المعرّف ⇒ الشريط بلا أوردر جديد، ثم البيانات الأصلية ⇒ نفس الرقم (نُفّذ محليًا
بمتصفح حقيقي: 6 محاولات حفظ ⇒ أوردران ومفتاحان وبند واحد لكل أوردر).

**«تكرار» من تفاصيل الأوردر في `/orders`**: في Network يحمل طلب `orders.duplicate` الحقل `operationId` والرد
`idempotency: "protected"`. تأكيد التكرار مع فقدان الرد ثم إعادة التكرار لنفس الأوردر (ولو بعد إعادة تحميل الصفحة) ⇒ «التكرار محفوظ
بالفعل — أوردر #X» ونسخة واحدة وسجل نشاط واحد؛ تكرار جديد بعد نجاح السابق ⇒ نسخة جديدة (عملية جديدة). (نُفّذ محليًا بمتصفح حقيقي.)

**إرسال الورشة** (المالك/مدير المخزون): نفس البنود 1–4 — إذن واحد وحركة مخزون واحدة لكل عملية (نُفّذت محليًا بمتصفح حقيقي:
11 محاولة ⇒ 6 أذون بالضبط).

## 4) تجربة الأدوار (معلّقة حتى تنفيذها)

دخول فعلي بحساب **المحاسب** و**مدير الحسابات** على Staging بعد 0045 والتحقق من الصفحات المسموحة/الممنوعة. لم تُنفَّذ بعد.

## 5) خطة الرجوع «توقف ومطابقة» (بعد 0051 — طريقة واحدة: إدخال أرصدة التوقف)

لا إعادة حركات V3 في V1/V2؛ تُدخل أرصدة لحظة التوقف **كفروق فوق أرصدة V1/V2 القائمة** (لا تضاعف، لا حذف تاريخ).

1. إطفاء V3 (لا يرفع حظر الكتابات القديمة):
   `node dist/scripts/disable-ledger-v3.mjs --tenant <t> --actor <ownerId> --reason "<سبب>" --apply --confirm "DISABLE LEDGER V3 TENANT <t>"`
2. إيقاف الشركة من لوحة المنصة (`tenants.status = suspended`)، و`TENANT_ACCESS_ENFORCEMENT_ENABLED=true` في بيئة التطبيق
   (السكربت يرفض بدونهما).
3. صورة التوقف — dry-run ثم apply:
   ```bash
   node dist/scripts/legacy-recovery.mjs snapshot --tenant <t> --actor <ownerId> --reason "<سبب>"
   node dist/scripts/legacy-recovery.mjs snapshot --tenant <t> --actor <ownerId> --reason "<سبب>" --apply --confirm "SNAPSHOT LEGACY TENANT <t> ON <db>"
   ```
   يطبع رصيد كل حساب V3 والبصمة ورقم الصورة.
4. ملف الخطة `plan.json` (يُعدّ ويُراجع مع المالك):
   ```json
   { "snapshotEventId": 0, "figuresHash": "<64 hex>",
     "cash": [{ "code": "OFFICE_CASH", "target": { "kind": "v1_treasury", "businessId": 0 } },
              { "code": "BANK_MAIN", "target": { "kind": "v2_account", "accountId": 0 } }],
     "acknowledgedNonCash": ["<كل حساب غير نقدي برصيد غير صفري>"],
     "zeroTargets": [{ "target": { "kind": "v2_account", "accountId": 0 },
                       "reconciledBalance": "<الرصيد القديم الحالي كما طُوبق>",
                       "explanation": "<لماذا لا مقابل له في V3 — 10 أحرف على الأقل>",
                       "evidenceRef": "<مرجع مستند المطابقة>",
                       "approvedByEmployeeId": 0 }] }
   ```
   كل حساب نقدي/بنكي/محفظة برصيد ← هدف واحد؛ كل حساب آخر برصيد يُذكر في `acknowledgedNonCash` (يُتابَع خارج V1/V2).
   **التصفير لا يُقبل لمجرد غياب مقابل في V3**: كل خزنة/حساب قديم نقدي برصيد خارج `cash` يجب أن يُحسم في `zeroTargets`
   بتفسير موثّق، ومرجع مطابقة، ورصيد مطابَق يساوي الرصيد الحالي بالضبط، واعتماد صريح من مالك فعّال لنفس الشركة.
   أي هدف غير محسوم (ناقص أو غير مطابق) يرفض التنفيذ كله برمز `unresolved`. الهدف لا يتكرر؛ خزنة V1 بمنزلتين فقط.
   التفسير والمرجع والاعتماد تُحفظ في حدث الاستعادة الدائم.
5. الاستعادة — dry-run (يطبع قبل/بعد/الفرق لكل هدف) ثم apply:
   ```bash
   node dist/scripts/legacy-recovery.mjs recover --tenant <t> --actor <ownerId> --reason "<سبب>" --plan plan.json
   node dist/scripts/legacy-recovery.mjs recover --tenant <t> --actor <ownerId> --reason "<سبب>" --plan plan.json --apply --confirm "RECOVER LEGACY TENANT <t> ON <db>"
   ```
   transaction واحدة: الرفع + الفروق + إعادة القراءة والمطابقة + حدث الاستعادة. أي اختلاف ⇒ إلغاء كامل (الحظر قائم، الشركة متوقفة).
   تكرار الأمر = replay بلا كتابة.
6. بعد النجاح فقط: مدير المنصة يرفع الإيقاف. إعادة تفعيل V3 لاحقًا تعيد الحظر تلقائيًا داخل معاملة التفعيل.

## ما لا يفعله هذا الدليل
لا تفعيل Ledger، لا Production، لا إجراء «احتفاظ بمستحق العميل» (معطّل)، لا SQL يدوي.
